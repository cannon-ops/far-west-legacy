## Pending Decisions

- **Render single-instance/stop-before-start assumptions — verified FWL-011-H3 (2026-08-10), one confirmed right, one confirmed WRONG.** Checked against Render's own docs (`render.com/docs/free`, `render.com/docs/deploys`, `render.com/articles/how-render-handles-zero-downtime-deploys`), not assumed, and cross-checked across two independent fetches. **(a) Single instance on free plan — CONFIRMED TRUE.** Render's docs list "scaling beyond a single instance" among what free web services explicitly don't support. **(b) "Deploys stop the old instance before starting the new one" — CONFIRMED FALSE, and it's the opposite.** Render does immutable, zero-downtime rolling deploys, with no free/paid distinction and no exception here (the one documented exception — a persistent disk disables zero-downtime deploys — doesn't apply; `render.yaml` has no `disk:` section, by design, since the ephemeral filesystem wiping `token_store.py`'s SQLite file on every deploy is the wanted behavior for bearer tokens). Real sequence: new instance boots and passes its health check *while the old instance keeps serving all traffic*, then traffic **switches** (a cutover, not a gradual split) to the new instance, then the old instance gets `SIGTERM` 60 seconds later (up to 30 more seconds grace before `SIGKILL`). **Practical impact on `token_store.py`:** each Render instance is its own container with its own ephemeral filesystem — the old and new instances do NOT share a SQLite file during that ~60–90 second overlap, the same way two gunicorn workers *inside one instance* do. A user whose `/auth/login` lands on the old instance a moment before cutover and whose `/callback` lands on the new instance after cutover hits the identical "Unknown or expired OAuth state" failure H3 fixed at the gunicorn-worker level — just now possible again at the instance-transition level. Same applies to an in-progress signed-in session or an in-progress M2.2 decisions file (`tmp/<job_id>.decisions.json`) spanning a deploy: lost, not corrupted — the user just has to redo that step. Requires `autoDeploy: true` (already on) to fire a deploy while a real user is mid-flow *and* the free instance hadn't already spun down from idling (a spun-down instance has no "old" instance to hand off from, so no overlap exists in that case) — a real but narrow window, not a hypothetical one, given a live demo/booth session could get pushed to during. **Design NOT changed here per this handoff's own instruction** (verify and report; H3's own report already scoped the fix as a Redis swap confined to `src/token_store.py` if this assumption turned out wrong — it did, so that fix is now a live option, Chief's call whether the narrow window is worth it before Chautauqua).
